# U1 Image Critic V4.1 交接文档

## 1. 交付目标

V4.1 的第一性原理是：找出图中明显错误的 artifact 与明显错误的文字，并把适合后续编辑模型局部重绘的区域框出来。

它不是通用审美评分器，也不是事实核查器。以下内容主动跳过：

- 年份、日期、当前事实等依赖世界知识的判断；
- 主观美观度、构图偏好和风格选择；
- AI 图片中不影响主体理解的轻微瑕疵；
- 置信度不高于 0.6 的候选问题。

文字是高优先级检查对象：每个意图可读的语义文字区块都应被覆盖，明显乱码、字形破损、扭曲、漏字、多字和可直接验证的内容错误不能遗漏。

## 2. 正式基线与成功语义

正式运行组合固定为：

```text
workflow = adversarial_consensus
coverage_mode = harness_v41
final stage = online consolidation
```

一个图片/工作流单元只有完成最终在线整编并写入 `results.jsonl` 才算成功。任何发现、质疑或裁决阶段异常，以及在线整编无法通过 schema/业务校验，都会在重试耗尽后写入 `errors.jsonl`。

`consolidate_existing.py` 是历史实验时期用于人工审查的排障工具，不能作为生产补偿机制。禁止在正式评估后离线补写、修改或伪装成功结果。

## 3. 全流程

```text
输入图片
  └─ 语义内容盘点与独立覆盖审计
       ├─ 文字通道：语义文字区块逐一检查
       └─ 非文字通道：独立实体/区域逐一检查
            └─ 多视图复核：原图 + 上下文 + 无损放大细节
                 └─ 发现者（Proposers，四类职责）
                      └─ 质疑者（Skeptic）逐候选验证与纠框
                           └─ 裁决者（Judge）基于候选 ID 裁决
                                └─ 在线整编与代码校验
                                     └─ 编辑模型可用的最终 bbox
```

### 3.1 语义覆盖 Harness

V4.1 不使用固定 3×3 切图。它先盘点主语义区块，再用独立盲盘点进行对账，并将文字与非文字覆盖状态分开记录。

每个语义区块至少产生一个文字检查要求或一个非文字 artifact 检查要求。代码负责生成确定性的原图、上下文视图和放大细节视图；裁剪仅用于看清细节，任何候选都必须回到原图和上下文中成立，裁剪边界造成的漏字或假问题会被拒绝。

当某个区块或通道检查失败时，Harness 会针对该区块执行恢复调用。若仍未覆盖完整，则：

- `coverage_status` 标为 `degraded` 或 `failed`；
- `findings_non_exhaustive` 标为 `true`；
- 总体置信度封顶为 0.5；
- 不允许把“没有合法候选”错误地等同于“没有问题”。

### 3.2 发现者角色

四个逻辑角色默认由同一个底座模型执行，通过不同 prompt 和结构化协议划分职责，并不要求四个不同 checkpoint：

| 角色 | 职责 |
|---|---|
| `anatomy_structure_topology` | 人体/动物解剖、对象形态、部件数量、连接、穿插、连续性和遮挡顺序 |
| `relations_physics` | 空间与物理关系、交互、支撑、重力、尺度、透视、阴影与反射 |
| `rendering` | 局部融化、破碎边界、重复纹理、材质断裂和其他明显渲染错误 |
| `text_coverage` | 盘点全部意图可读文字，只报告明显字形破损、乱码或可直接验证的文字错误 |

非文字角色发现的文字问题会被路由到文字处理逻辑，防止职责重叠造成重复候选。

### 3.3 质疑者与裁决者

质疑者（Skeptic）逐条检查候选是否有直接可见证据、是否属于核心问题、是否可能由风格/反射/模糊/透视/遮挡造成，并可修正 bbox。

裁决者（Judge）只能引用已有候选 ID，不得凭空新增问题。代码在裁决后执行确定性门控，只保留：

- `verification = supported`；
- `materiality` 为 `major` 或 `critical`；
- `confidence > 0.6`；
- bbox 合法且不是近全图框；
- 问题在原图及上下文中成立。

### 3.4 在线整编

最终整编将来源候选按语义与空间关系分批，每批最多 10 条，然后执行全局合并校验：

- 同一个局部重绘目标存在多个问题时，只保留一个 bbox，并合并问题描述；
- 空间独立、需要分别重绘的实体保持多个 bbox；
- bbox 可保留少量上下文冗余，不要求贴边，但实体或语义区块独立性优先；
- 禁止重复框、近全图框以及大框套住多个已经准确定位的小框；
- 每个来源候选必须被保留或以中文理由明确丢弃，来源 ID 必须守恒；
- 结构或业务校验失败时，依次执行整编修复与全局修复；全部失败则整个单元失败。

## 4. 分类体系

正式 taxonomy 包含六类：

| 维度 | 枚举值 | 含义 |
|---|---|---|
| Artifact | `rendering_artifact` | 局部渲染、纹理、边界、材质错误 |
| Artifact | `structural_artifact` | 实体形态、解剖、部件与比例错误 |
| Artifact | `topology_artifact` | 融合、连接、穿插、连续性与遮挡错误 |
| Artifact | `relational_physical_artifact` | 关系、交互、尺度、支撑、阴影和物理错误 |
| Text | `text_visual_integrity` | 字形破损、融合、扭曲、笔画异常或不可辨认 |
| Text | `text_content_fidelity` | 明显乱码、漏字、多字或可直接验证的内容错误 |

无参考文字时不得臆造目标文案；只有图内存在清晰、可直接验证的预期内容时才报告内容保真问题。

## 5. bbox 协议

所有涉及 bbox 的模型输入输出、业务对象、trace、JSONL、整编结果和 HTML 数据均使用同一坐标系：

```text
bbox_norm = [x1, y1, x2, y2]
x, y 均为整数，范围 [0,1000]
(0,0) 是左上角，(1000,1000) 是右下角
x1 < x2，y1 < y2
```

报告页面直接依据 `bbox_norm` 在前端绘框，不生成带框副本图片。

## 6. 输入与防泄漏

`--input-root` 递归发现图片。若指定 `--input-jsonl`，则只处理 allowlist 中的图片，并保持 JSONL 顺序；默认路径字段是 `image_absolute_path`。

输入路径只用于程序读取、manifest 和图片服务。模型请求只包含管线 prompt、结构化上下文和图片像素，不发送目录名、父目录标签、文件名或参考答案标签。接入新的数据读取器时必须继续保持这一约束。

正式全量运行需要显式提供 `--all --confirm-run-all YES`，防止误触发。建议任何新模型或新服务先用 `--limit-images 1` 冒烟，再扩大到小批量。

## 7. 模型接口

当前适配器使用 OpenAI-compatible `POST /v1/chat/completions`：

- 图片以内嵌 data URL 发送；
- 首选函数工具 `submit_result` 返回结构化结果；
- 工具调用不可用时允许纯 JSON 回退；
- 自然语言字段强制使用简体中文，字段名、枚举、ID 和坐标保持 schema；
- 默认 `temperature = 0`；
- API Key 只从 `--api-key-env` 指定的环境变量读取；
- trace 会脱敏 authorization、API key、图片 data URL、源路径和文件名。

服务必须支持多图消息、tool calling 或合法 JSON 输出，并允许足够的输出 token。首次接入应检查 `traces.jsonl` 中的 transport、解析结果和重试原因。

## 8. 重试与并发

- 单次模型请求：`--retries 2`，即最多 3 次尝试；
- 在线整编：`--consolidation-retries 2`；
- 完整图片/工作流单元：`--unit-retries 2`，失败时从头重启；
- `--max-in-flight`：全局同时在途模型请求上限；
- `--max-images-in-flight`：同时运行的图片/工作流单元上限。

不要直接照搬高并发配置。先确认模型服务的实例数、队列容量、超时与限流策略，再逐步上调；过高并发会放大尾延迟与重试，未必提高有效吞吐。

## 9. 输出与状态判断

| 文件 | 作用 |
|---|---|
| `manifest.json` | 输入根目录、图片 ID、相对路径和绝对路径映射 |
| `run_config.json` | 模型、接口、并发、重试、版本和坐标协议 |
| `results.jsonl` | 正式成功单元；最终结果在 `consolidated_result` |
| `errors.jsonl` | 重试耗尽的失败单元 |
| `traces.jsonl` | 阶段、请求、响应、重试和覆盖轨迹 |
| `index.html` | 运行 `u1-critic-v41-report` 后生成的可视化 |

判断一张图片是否成功时，应以 `results.jsonl` 中存在 `status=ok` 且包含通过校验的 `consolidated_result` 为准，不能只看前置 `result`，也不能把覆盖完整度等同于识别正确率。

断点续跑以 `results.jsonl` 中已经成功的 `(sample_id, workflow)` 为准。失败项不会被视为完成，再次以相同输出目录运行时可重新执行。

## 11. 已验证基线

交付前已有的代表性实验结果：

- 内部 27B 模型，30 张测试集：失败项重跑后 28 个在线成功、2 个严格整编失败；
- TokenEvol GPT-5.6-sol，30 张测试集：30/30 在线成功；
- 内部模型，211 张任务：210 个在线成功、1 个嵌套框整编失败；成功项中 181 个覆盖完整、29 个覆盖不完整，得到 315 个最终编辑区域；持久化的 7051 个 bbox 均满足整数 `[0,1000]` 契约。

这些数字是特定模型服务和数据批次的工程验证，不代表通用精度指标。交付包本身不包含这些实验图片、结果或服务地址。

## 12. 性能现状与观测缺口

在上述 211 张内部模型任务中，平均约 68.2 次模型调用/图，其中 `content.inspect.multiscale` 平均约 52.1 次/图，占总调用约 76.4%，是主要耗时来源。

历史 trace 的请求计时在进入全局 semaphore 之前开始，因此混入了排队等待；同时没有记录每个完整图片单元的起止时间。不能用“批次总时长 ÷ 图片数”推断真实单图处理耗时，也不能把旧 trace 的 request duration 直接当纯服务推理时间。

后续性能优化应先补充以下指标，再基于实测改动：

- `unit_elapsed`：完整单图管线墙钟时间；
- `queue_wait`：等待全局并发令牌的时间；
- `request_elapsed`：实际 HTTP 请求时间；
- 各 stage 的调用次数、总耗时、P50/P95 和重试率。

在不改变语义覆盖的前提下，优先尝试区域微批处理：文字每批约 2 个语义区块、非文字每批约 4 个区块，并由代码校验返回的 region ID 是否完整。该优化尚未作为 V4.1 基线实现，交接方不得在没有回归评估时直接替换正式版本。

## 13. 已知限制

- 27B 模型的结构化输出、覆盖稳定性和最终整编仍可能波动，Harness 能降低但不能消除基础能力上限。
- 发现者、质疑者和裁决者默认共享同一底座模型，角色分离不能完全抵消系统性偏差。
- 覆盖完整只表示既定语义区域被执行过检查，不等于模型一定理解并发现了其中所有错误。
- 文字密集图仍是高风险场景，需重点观察漏判、重复合并和过大语义框。
- 严格禁止嵌套编辑容器会让不稳定模型在整编阶段失败；这属于正式失败，不能事后补写。
- 完整 trace 体积较大。HTML 建议用 `--omit-model-traces` 压缩页面，但磁盘上的 `traces.jsonl` 应保留用于审计。

## 14. 新使用者验收清单

1. 使用干净环境安装 wheel 或源码，四个 CLI 均能执行 `--help`。
2. 配置环境变量中的 API Key，不把密钥写入脚本、配置、日志或交付包。
3. 用 1 张图冒烟，确认工具调用/JSON 可解析、bbox 为整数 `[0,1000]`、在线整编成功。
4. 用 5 至 10 张文字与非文字混合图片小批量运行，检查 `coverage_channels`、重试和失败原因。
5. 生成 HTML，核对原图映射、序号框与详情是否一致，确认没有全图框、重复框或大框套小框。
6. 再按服务能力调整并发并运行全量；保留 `run_config.json`、全部 JSONL 和模型版本信息。
7. 若修改 prompt、schema、coverage、门控、整编或坐标协议，必须建立新版本并回归，不得继续称为原始 V4.1 基线。

## 15. 交付边界

本包包含可安装源码、测试、设计记录、静态管线说明、运行示例和交接文档；不包含任何模型密钥、内部服务地址、原始图片、数据集标签或历史实验结果。

接收方首次正式运行前，应自行确认图片数据使用权限、模型服务容量和输出保存策略。
